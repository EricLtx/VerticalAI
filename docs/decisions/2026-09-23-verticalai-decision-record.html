1. Vision and value ladder

VerticalAI is a self-improving, peer-to-peer, local-first orchestration runtime for businesses — from a one-person company to the employees of a large enterprise. The business owns everything it accumulates; that userland is movable, replicated across the business's own machines with no cloud dependency, and shareable within a trade through a curated federation. Cloud models are optional arches, never a dependency.

Analogy kept internally: "Linux for AI". A small kernel inspired by micro-architecture — orchestration (pipeline/scheduler), registers, locks — with everything else in userland. Models are the instruction set; the kernel's task-state IR is the common intermediate representation that lets heterogeneous models cooperate. Externally the product is described as an orchestration runtime, not an "AI operating system" (CRA Annex III wording; see §14).

2. System topology

One shared userland per business, replicated across its own nodes; a phone acts as a thin node for human approvals; a headless node may host arches and relay traffic; cloud arches are reached only through the kernel and only within clearance. Businesses in the same trade share modules through a curated federation.

3. Kernel / userland boundary

The kernel owns only mechanism: scheduling, the registers (task-state IR), the lock surface, STOP, principals, the arch layer, storage tiering, the ledger, replication mechanics, and the interceptor chain. It refuses to own any domain knowledge, skill, business memory, policy, specific model, application driver, channel or user interface. Anything policy-shaped is a userland object the kernel reads and enforces but never writes on its own initiative.

4. Registers: the task-state IR as a blackboard

A register set holds the state of one task in a model-agnostic form: goal, constraints, evidence with origin taint, decisions, open questions, artefacts by hash, and classification labels. Every hand-off between arches goes through the IR — never through one model's native transcript. Verified fact behind this: provider-side reasoning state (e.g. Anthropic thinking blocks) is bound to the producing model and dropped by any other; kernel-owned state is what makes model swapping mid-task possible.

Arch identity is content-addressed. Weights hash, engine + version, backend, quantisation, KV-cache type, threads, batch, sampling, seed — any change is a new arch id (Component Configurator event). A peer's network-reached model is a distinct arch.
Learning modes per artefact class (policy, visible in the UI): cloud-assisted, derived-only (frontier arches see only declassified outputs), local-only (no machine authoring; memory, search, teaching and imported modules remain).

5. Lock surface and partitions

The original arbitration was "one lock primitive with a holder kind {machine, human}". The adversarial review showed it cannot carry its three uses under partition: exclusivity for an irreversible action is a consensus property, and "human locks are local by nature" is exactly what lets two humans each hold "the" lock. The revised arbitration keeps one syscall surface with a tagged union.

6. Invariants and the interceptor chain

Only decidable invariants are kernel interceptors. The Annex III classifier and the declassification gate are userland gate policies whose signed verdicts the kernel requires on promote, export and import. All five invariants are property-tested on the SP0 stub kernel.

Inv.Statement (as restated after review)SP0 evidence
I1An approval of kind human can only be produced by a human ceremony; no machine principal can produce or forge it; the human path (STOP, override, approval) is always reachable — no queue, budget or partition can starve it.property test: no sequence of machine syscalls yields a human approval; human STOP always accepted
I2No object whose classification exceeds a principal's or arch's effective clearance is ever projected into its reachable set. Every object written by a task inherits the join of the labels it read; declassification is explicit and measurable.property test: no register label ever reaches an arch above its clearance
I3A merge never silently discards a write; conflicts are resolved by a declared rule or surfaced, and logged. Logged shred events are the one sanctioned deletion.property test: every write survives any merge order (kept or surfaced)
I4Machine principals run non-human-initiated automations only while an autonomy liveness lease, renewed by a human-capable node, is unexpired and no STOP is active in scope.property test: no automation after lease expiry; STOP blocks until RESUME cites it
I4'Every adapter reports its real context budget; infer refuses an over-budget lowering or applies a logged structural projection — never a silent truncation.property test: projected ⇔ ledger entry exists

7. Human ceremony, STOP and liveness

No syscall accepts a caller-asserted principal; the kernel derives it from the authenticated channel. "Human" is a hardware-key ceremony bound to one action digest, short-lived. STOP needs presence only; authorising writes need verification. The phone is an approval channel, never a lock home.

8. Storage tiering and the ledger

The original arbitration "Automerge for all mergeable state" was narrowed: full operation history is permanent in a CRDT, tombstones erase nothing, and secrets or traces would replicate to every phone. Three tiers now.

9. Distribution: partitions and merge

Keep working offline, merge on reconnect, with merge rules per resource class (LAN / VLAN / WAN). Policies merge most-restrictive-wins; STOP, shred and human-override events win merges; "current Hot version" is a set resolved most-restrictive, never a scalar last-writer-wins. Sovereignty restated: no third party ever holds plaintext or performs inference; connectivity may use untrusted, self-hostable relays that see ciphertext only.

10. Userland object model

Six families; all versioned, mergeable, carrying a classification label and a provenance manifest (content hash, lineage, signer, arch compatibility, cost/applicability contract, origin taint summary).

11. The vertical process: Cold → Warm → Hot

The literature is unambiguous: self-authored skills are net negative without a hard verifier; success-only telemetry never yields a useful skill; ungated accumulation collapses and rollback recovers little. So the loop is sparse search with the gate at the front.

12. Learning signals and the threshold

Phase 1 signals (decided): shadowing and technology watch; explicit teaching later. Shadowing captures, within a user-chosen allow-list, artefact created/modified with diff, tool used, duration — no keystrokes, screenshots or page text outside the allow-list; special-category data dropped at ingest. Every trace carries an origin taint {owner-authored, owner-shipped, third-party-inbound, web} and a data class {own, third-party-mandated, unknown} assigned by source. Traces are personal-scope and non-exportable; only derived, declassified candidates move. Technology-watch candidates carry taint web and reach Hot only through human approval.

Threshold (decided, then made two-dimensional): data maturity (volume, artefact-type diversity, lawful-basis coverage) AND verifier readiness per artefact type. VerticalAI sets a floor at which the process fires once automatically for ready artefact types; the owner then owns and adjusts the threshold and is signalled before later runs.

13. Scopes and the curated federation

Three value scopes; each transition is a promotion with the same gates. The vertical scope is part of the product: "the first P2P runtime that brings value and adoption to businesses, local-first". The trust model is a curated federation that decentralises progressively.

Founder arbitrations during brainstorming (22 Sep 2026)

Question raisedArbitration
What does the kernel own?Micro-architecture analogy: orchestration, registers (memory), lock/semaphore concept applied to AI. The rest is userland — that is what makes the product movable.
Which lock semantics?All three: resource mutual exclusion + resource allocation for the scheduler; mutation gating; human-held semaphores. Human-in-the-loop is a concept CARS puts on top: policy in userland, but the kernel keeps a primitive guaranteeing it is available at all times.
Which models?None specific; one or a combination; open-source local and big providers (Fable cited) are both legitimate arches. Any AI system — JEPA world models, System-1-style, NLP, future paradigms — must be characterisable.
Decentralised how?Several kernels on several nodes sharing one userland, no cloud, P2P propagation with management on top — the same value for a one-person company and a large enterprise.
Partition behaviour?Keep working, merge on reconnect with configurable merge rules (LAN/VLAN/WAN) — the most evolutive option.
Where does Claude Code sit?Corrected: the OS schedules Claude Code when needed; harnesses are opaque userland processes under a lease.
What is a node?Computation as close to the system as possible with a minimum performance floor; a configurable share of machine resources; native on Windows (most businesses), Linux and macOS; must live on the same host as the applications it integrates.
Which learning signals first?Shadowing and technology watch; explicit teaching afterwards. The owner must understand what is built and keep decision-making and personalisation.
Is the vertical scope part of the product?Yes — a wider end point in clients and an innovation: the first P2P runtime bringing value and adoption to businesses, local-first.
Trust model of the vertical scope?VerticalAI curates first; curation is delegated to businesses with enough usage; end state: businesses checking each other and allowing connection ("vertical partnership"). Curated federation with the founder as signer for now.
First trade?Freelancers and SMEs offering services/products — not the founder's audit practice — because SME owners lack the skills and tools to find relevant use cases and many already sell AI-made work.
Week-one behaviour?CARS-style register first: inventory of models and tools with all metadata (conversations, usage, licences, master prompts) into one local workspace; a threshold with a floor that fires the first run automatically, then owner-adjusted; all trades, not just quotes and emails.
